0.15.x → 0.16.x
===============

Add each change under the matching section below as it lands, and name the migration's ``unique_id`` wherever a
breaking schema change ships one (see :ref:`migrations_reference`). Remove the sections that stay empty before the
release.


Breaking — YAML schema
----------------------

* ``J1939Frame`` names must be unique within a :class:`~flync.model.flync_4_bus.can_bus.CANBus`. A J1939
  frame is addressed by name (``J1939FrameRef.frame_ref``), so a bus that declares two J1939 frames with the
  same ``name`` no longer loads (``FLYNC-BUS-MAJ-UNIQ-426``); previously the later frame silently shadowed
  the earlier one. Rename one of the frames. Classical ``CANFrame`` / ``CANFDFrame`` names remain free-form.

* ``J1939FrameRef`` (``j1939_sender_frames`` / ``j1939_receiver_frames``) addresses its frame by
  ``frame_ref`` (the frame name) and/or ``can_id`` (the full on-bus CAN identifier, Source Address in its low
  byte) instead of ``pgn``. A J1939 reference resolves by name or identifier, so a bus may carry several J1939
  frames that share a Parameter Group Number, and a bus reached by a J1939 node may also carry classical CAN
  frames.

  .. code-block:: yaml

     # before
     j1939_sender_frames:
       - pgn: 61441

     # after
     j1939_sender_frames:
       - frame_ref: Frame_EBC1

  **Migrated** by ``v0_15_to_0_16``: ``pgn`` is replaced with the name of the J1939 frame with that PGN on the
  interface's bus, which 0.15 kept unique. A ``pgn`` that names no frame is left unchanged and a warning is
  logged.

* :class:`~flync.model.flync_4_ecu.lin_interface.LINFrameRef` (``sender_frames`` / ``receiver_frames`` of a
  LIN master or slave) drops ``bus_ref``. It was never read: a LIN frame reference always resolved on the
  ``bus_ref`` of the owning interface, as CAN and J1939 references do.

  .. code-block:: yaml

     # before
     receiver_frames:
       - bus_ref: BodyLIN
         frame_ref: 1

     # after
     receiver_frames:
       - frame_ref: 1

  **Migrated** by ``v0_15_to_0_16``: ``bus_ref`` is removed from every LIN frame reference.


Additive — YAML schema
----------------------


Namespaces for PDUs and SOME/IP
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
``communication/someip/services`` and ``communication/channels/pdus`` accept sub-folders. A service or PDU
in a sub-folder is named ``<folder>::<name>`` (nested folders join, e.g. ``abc::def::<name>``); one stored
directly in the folder keeps its name. Reference a namespaced PDU by its qualified name in ``pdu_ref``.


New field: ``lite`` on MII
~~~~~~~~~~~~~~~~~~~~~~~~~~

:class:`~flync.model.flync_4_ecu.mii.MII` gained ``lite`` (default ``false``) for MII-Lite, which drops TX_ER, RX_ER, CRS and COL
and so carries full duplex only. New validation: ``FLYNC-CMN-WARN-COMP-431`` and ``FLYNC-CMN-MAJ-CONS-432``, see :doc:`../error_catalog`.


New xMII type: QSGMII
~~~~~~~~~~~~~~~~~~~~~

``mii_config`` on :class:`~flync.model.flync_4_ecu.port.ECUPort`, :class:`~flync.model.flync_4_ecu.switch.SwitchPort`
and :class:`~flync.model.flync_4_ecu.controller.EthernetInterfaceConfig` also accepts
:class:`~flync.model.flync_4_ecu.mii.QSGMII` (``type: qsgmii``), four 10/100/1000 Mbps channels over one serial link, without
a Packet Control Header. It is also accepted as a port extender uplink, including a channelized one.

New validation: ``FLYNC-ECU-MAJ-VAL-428`` to ``FLYNC-ECU-MAJ-VAL-430``, see :doc:`../error_catalog`.

New optional variability domain
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The optional ``variability/`` folder (:ref:`flync_4_variability <variability>`) turns a workspace into
a 150 % model of a product line: ``variability/feature_model.flync.yaml`` declares the features, and
``variability/variants/*.flync.yaml`` declares the product variants as feature assignments.
``flync_model.variability`` is ``None`` without the folder, so a 0.15 workspace keeps its layout and
loads exactly as before.

A feature declares ``name``, ``description``, an optional ``type`` (``boolean`` or ``enumeration``,
inferred from ``values`` when omitted), ``category`` (``product``, ``context``, ``requirement``,
``solution`` or ``element``), ``values``, ``ordered``, ``default``, and free-form ``attributes``. The
feature model declares ``features`` (a flat list), ``constraints`` (``expression`` / ``description``),
``qualifiers`` and ``default_variant``.

A variant declares ``description``, ``extends``, and ``features`` (its decisions; undecided features take
their default, decisions are inherited along ``extends``).

With the folder present, a new reserved key ``variant_condition`` is recognized in two places, since a
product variant is a selection of ECUs and of the links between them: at the root of an ECU's
``ecu_metadata`` it decides which variants the whole ECU folder is part of, and on an entry of a list in
the system topology (``topology/``: a connection, a node of a multidrop segment) it decides which variants
the entry is part of. An ECU is otherwise the same in every variant it is part of; an ECU that differs is a
separate ECU. A ``variant_condition`` anywhere else, and a ``variant_values`` key anywhere, is an error
(``FLYNC-VAR-MAJ-STRUCT-483`` to ``FLYNC-VAR-MAJ-STRUCT-486``). The conditions are resolved by the loader for
the selected variant before validation, so no other model sees them; using one without a ``variability/``
folder is an error.

New fields: ``sender_frames`` on LIN slaves, ``receiver_frames`` on the LIN master
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

:class:`~flync.model.flync_4_ecu.lin_interface.LINSlaveInterface` gains ``sender_frames`` and
:class:`~flync.model.flync_4_ecu.lin_interface.LINMasterInterface` gains ``receiver_frames``, both lists of
``LINFrameRef`` that default to empty. Master and slave interfaces now read the same way, as CAN
interfaces do: ``sender_frames`` lists the frames whose payload the interface transmits, and
``receiver_frames`` the frame it wants to receive. The master transmits the headers of all frames in the bus
schedule tables. A frame sent by the master goes to slaves, one published by a slave goes to the
master and/or to other slaves.

The master's ``sender_frames`` used to list every frame it schedules. Existing documents load unchanged
and read as the master publishing all of them, which is what they described while slaves had no
``sender_frames``.

New validation: ``FLYNC-CMN-MAJ-UNIQ-489``, a LIN frame listed in the ``sender_frames`` of more than one
interface; a frame has exactly one sender. See :doc:`../error_catalog`.

New validation: ``FLYNC-TOP-MAJ-CONS-490``, a frame listed in a LIN interface's ``sender_frames`` or
``receiver_frames`` that appears in none of the bus's ``schedule_tables``. The master issues a header only for
scheduled frames, so such a frame would never be transmitted. Add the frame to a schedule table with a fitting
period; the period is an authoring decision, so no migration is provided. See :doc:`../error_catalog`.
